## The design, briefly

I don't want to spend too much time on how to design a URL Shortener, since it is System Design 101 and has been covered to death.

If it's new to you and you'd like to learn about design choices and trade-offs, you can read more about it in [ByteByteGo](https://bytebytego.com/courses/system-design-interview/design-a-url-shortener).

Here are the most important decisions made for the system I'm showcasing:

1. 100M urls a day equals around 1.2k writes and 11.6k reads per second. I aimed for a total of 10k rps with that same 10:1 ratio of reads to writes, as a real url shortener would see
2. I use MD5 hashing. With 365B urls (100M a day for 10 years), collisions are still very unlikely, and if *a few* collisions happen, they'd have negligible difference in overall latency. Plus, when using hashing, I don't need to maintain a separate service such as ZooKeeper for centralized ID generation (you'd need that for approaches such as base62 encoding when scaling your API horizontally). As a consequence, my overall system ends up being simpler, with fewer moving parts.
3. I'm not concerned with storing all urls for 10 years since I wouldn't have the storage capacity in my system (~28TB for my use case). I treat URLs as expiring after 24 hours (*which I have not yet implemented, due to my laziness*) which caps storage at around 8GB.
4. I use temporary redirects (HTTP status code 302) instead of permanent redirects (HTTP status code 301) to allow me to capture click rate (*and haven't implemented it either. Have I already mentioned I can be lazy?*).
5. Use a cache (Redis) in front of a database (Postgres) for reads

Overall the design is quite vanilla, and looks like this:

## It works on my machine

Local development was pretty uneventful. After writing the Go code for the API, I decided to go with a Docker Compose setup running the design above, and use k6 for running load tests.

You can find them on GitHub since the repo is public:

1. [Docker Compose](https://github.com/GilbertoCunha/system-design/blob/main/url-shortener/docker-compose.yaml)
2. [k6 load tests](https://github.com/GilbertoCunha/system-design/tree/main/url-shortener/test/load)
3. [Taskfile](https://github.com/GilbertoCunha/system-design/blob/main/url-shortener/Taskfile.yaml): I use it as a `Makefile` replacement so I can more easily run common commands from there

I made no adjustments to the Postgres connection pool, so my application used the defaults of [pgx](https://github.com/jackc/pgx), the Go library I use to talk to Postgres. For Redis, through [go-redis](https://github.com/redis/go-redis), I set a modest pool of 20 connections.

More interestingly, I didn't specify resource limits for any container in the Docker Compose file - who needs that, right?

When running load tests with k6, this meant that my API, Postgres, Redis and k6 itself were sharing my laptop's resources and were free to use as much as they needed, so long as my laptop could keep up.

k6 was configured such that it would ramp up requests for a while until it hit 10k rps, and then maintained that request throughput - I called this the `steady` phase of the load test.

For reference, my laptop is a MacBook M4 Pro, with 12 cores and 24GB of unified memory.

Off to the races I went, and ran a load test for 10k rps:

- 10k clean rps
- 0 errors
- 1.23ms p99 during `steady` phase

Look at me! This is pretty easy, right? *I'm going to the major leagues*.

Or at least that's what I thought, but then an older, less efficient CPU, over-contended for many other resources came into the picture - my homelab.

And so the rabbit hole started.

## The homelab and its network

To understand many of the limitations that came along, I need to explain what my homelab looks like.

Basically, I got a Hetzner server at an auction and configured it with:

- [Headscale](https://headscale.net/stable/): self-hosted tailscale, so I could create my own private mesh network for things I didn't want to expose to the public internet (many of the services I run in my cluster)
- [Proxmox](https://www.proxmox.com/en/): I use it mainly as a hypervisor so I can provision VMs inside of the server to use as Kubernetes nodes
- [Talos Linux](https://www.siderolabs.com/talos-linux): an OS made for Kubernetes, which I run inside each VM

At the moment I am rocking 3 VMs - one control plane node, one system node (for running all of my services) and one worker node (for running my applications). Yes, I have downtime when updating any of those nodes, but I can live with it on my modest box.

To be transparent, I initially had way more VMs. Trimming it down to 3 was part of the optimizations I did for the URL shortener in order to reduce network hops between VMs - which reduced p99 latency from 493ms down to 96 ms.

Regardless, I lost most of the metrics and dashboards I had during those benchmarks except some numbers I had written down (oops!), so I'll keep them out of this post.

Of course, I needed to take care of carving out IP ranges specifically for nodes, pods and services, also taking into account that Kubernetes nodes needed to enter the mesh network, and configured IP forwarding on the host server to the Proxmox VMs. I won't go into too many details as to how, as the homelab might earn its own blog series, but I figured it was worth a mention in passing.

Alright, so what exactly is the network path between a client and the Kubernetes pods running in my homelab? It depends on whether you're trying to access them while on the mesh network or the public internet. It looks more or less like this:

![cluster-networking](/url-shortener/cluster-networking.png)

*Yes, I purposely kept the host ip forwarding out of the picture to keep things simple*. Some additional context:

1. The diagram above does not show it, but I am using [Cilium](https://cilium.io) as the Container Network Interface plugin for my cluster. This will be relevant later (wink, wink).
2. I have two separate [Envoy](https://www.envoyproxy.io) Gateways (following Kubernetes [Gateway API](https://kubernetes.io/docs/concepts/services-networking/gateway/)) serving as an L7 proxy for my applications. These are separate for mesh and public traffic. I am using [kgateway](https://kgateway.dev) as the Gateway Controller.
3. I wanted to experiment with Cloudflare tunnels, so I created one and deployed [cloudflared](https://github.com/cloudflare/cloudflared) on the cluster. This allows my applications to be reached from the public internet without my host needing any additional open ports to the outside world. It's pretty cool, but comes at a price (more on that later).

This is a pretty standard setup for networking in Kubernetes (with cloudflared being a little more niche), so I thought I wouldn't need to worry about it that much.

*Spoiler alert*: it came to bite me in the ass, but we'll get there.

Besides that I also have a bunch of other services running in the cluster that I'll just mention here in passing:

- [ArgoCD](https://argo-cd.readthedocs.io/en/stable/): for GitOps

And a few more, but you get the main idea: *I have a bunch of other stuff running in my modest box*.

## Maybe it only works on my machine...

Alright, so we got to 10k rps first try locally, time to deploy!

In my cluster, however, I am quite strict with pod resources and limits - which I had not set with Docker Compose locally. As such, I had to set some numbers for CPU and memory for my API, Postgres and Redis.

So I did what any sensible person would do and pulled those numbers out of my ass.

I decided, in my infinite wisdom, to set:

- API at 500m CPU and 200Mi with no `GOMAXPROCS` or memory limit for Go
- Postgres at 500m
- Redis at 500m without `maxmemory`

Deploy and...

*What??? Maximum 3.5k clean requests per second? During the `steady` phase of the load test only 180 requests per second succeeded? What do you mean?*

![d1-journey](/url-shortener/d1-journey.png)

This screenshot was taken from a run I replicated after the fact. At this point in time I had no instrumentation and didn't have a nice dashboard to tell me what went wrong. All I knew were the summary numbers k6 spits out at the end of a load test run.

With that, my dreams were shattered. I did, however, make a smart decision that eventually culminated in me writing this post right now: instead of mindlessly tweaking and re-running tests until I eventually stumble into a good configuration, **let's measure first**.

And so I began instrumenting my code.

## Seeing inside

At first I pretty much only used Prometheus to instrument HTTP responses from my API. As I did more and more experiments, my instrumentation grew so I could better pinpoint errors.

In later sections, I will explain what I wasn't measuring at the time, and how that misled me - which leads to a nice story of how metrics can deceive you as to what your system's bottlenecks are.

From all of the metrics I gathered, I then built a nice looking dashboard which presented all the information I needed to properly identify problems with my system.

Here's what I ended up with:

- **Top level metrics**: p99 latency, req/s per status code, error rate burn, ...
- **Host metrics**: resource usage, CPU pressure (share of time work waits for a CPU in each Kubernetes node), CPU steal (share of time a Proxmox VM wanted CPU, but Proxmox gave it to another node)
- **Gateway metrics**: in-flight requests, resource usage, latency as seen from the gateway, ...
- **API metrics**: latency per route, errors by status code, average latency broken down (waiting for a connection, waiting for a response from db or cache, running actual API level code, ...), resource usage, ...
- **Go metrics**: Go scheduler wait time and share of CPU used for garbage collection
- **Redis**: resource usage, pool usage, command latency, errors by type, cache hit ratio, ...
- **Postgres**: resource usage, pool usage, query latency, errors by type, ...

*Don't hold your breath while reading all that. I know, it's a lot!*

Here's an example of what the landing page for the dashboard looks like:

![dashboard-landing-page](/url-shortener/d0-journey.png)

It also contains annotated queries so I can see load test runs (the purple area in the background), new deployments, OOM Kills, etc... It's pretty neat, and it evolved quite a lot with the help of *Cláudio* (the Portuguese name I jokingly use for Claude) after I got bored with doing everything manually.

Most of these metrics were already exposed by the services I already had running in Kubernetes. There were two interesting tweaks I needed to do for Postgres and Redis, though:

- `pgx`, the library I used to talk to Postgres in Go, exports Pool metrics (connections in use, idle, ...) as **Gauges**. The problem with gauges is that they are *point in time* metrics: they tell you what's happening *right now*, but nothing else. Since I had setup polling every 5 seconds from Victoria Metrics, this meant everything happened in between was lost. When there were spikes, I could even get the impression that the pool was doing fine when it was indeed choking in between the two scrapes.
- `go-redis` has exactly the same problem

The solution I came up with was simple: record every wait for a connection in a **Histogram**, so no wait can hide between two scrapes, and count the seconds each connection is held in a **Counter**, whose rate is the average number of connections in use. Implementing this solution for `pgx` or `go-redis` is slightly different, though:

- `pgx` has an `.Acquire()` method that allows you to explicitly acquire a connection from the pool in your Go code. This means that timing it is simply a matter of calculating the time this `.Acquire()` takes. Pretty easy.
- `go-redis` has no such method. It acquires and releases connections from the pool on its own. So, I created my own [counting semaphore](https://github.com/GilbertoCunha/system-design/blob/main/url-shortener/internal/storage/redis/store.go) using a buffered Go channel and timed how long it took to acquire a slot from the semaphore.

With that out of the way and the code instrumented, I was ready to figure out more reliably what the first bottleneck was.

From here on out, all results and conclusions you'll see were derived from this beautiful dashboard.

## Giving it room

Alright, let's figure out why my homelab can only handle 4k rps. Run load test again, check the dashboard, and...

![d1-throttling](/url-shortener/d1-api.png)

Well, that explains it... The API gets CPU throttled, the Go scheduler needs to wait more and more until it can keep working, requests queue, everything goes to hell...

Why so bad? Go reads the container's CPU limit, but it never runs on fewer than 2 threads. With a 500m limit, 2 threads use up the whole quota in the first half of every 100ms period, and then get paused for the rest of it.

And why did it collapse to 180 req/s instead of just staying at 4k? Once requests queue for longer than their timeouts, the API spends its little CPU on work that clients have already given up on. Almost nothing finishes in time.

Not an amazing insight from the dashboard, raising the CPU limit is probably the first thing I'd do, but hey! At least we're making data-driven decisions, right?

So much for those requests and limits numbers I pulled out of my ass...

Alright! Increase API CPU limits to 3 - including `GOMAXPROCS`. That section of my deployment looked like this:

```yaml
apiVersion: apps/v1
kind: Deployment
...
      - containers:
        - name: api
          env:
            - name: GOMAXPROCS
              valueFrom:
                resourceFieldRef:
                  containerName: api
                  resource: limits.cpu
                  divisor: "1"
            - name: MEMORY_LIMIT_BYTES
              valueFrom:
                resourceFieldRef:
                  containerName: api
                  resource: limits.memory
                  divisor: "1"
            ...
          resources:
            requests:
              cpu: 1
              memory: 100Mi
            limits:
              cpu: 3
              memory: 500Mi
```

Also increase Postgres CPU limits to 2, Redis to 1 just for good measure, plus a few memory settings (`maxmemory` for Redis, Go's memory limit) and pools of 20 Postgres and 50 Redis connections... (*I have not been the most careful using the scientific method of changing only a variable at a time to know what impact came from where, but alas*)

Run again, and:

![d0-journey](/url-shortener/d0-journey.png)

Nice! Managed to hit 10k rps, no errors, 8ms p99 (70ms when seen from k6 due to latency from laptop to Hetzner server). We finally did it!

I took a second to appreciate what I had done to get this working. What marvelous beauty.

And then, completely dismissing the achievement that happened 5 seconds ago, for it is now in the past, I thought: *I wonder how much further I could go?*
