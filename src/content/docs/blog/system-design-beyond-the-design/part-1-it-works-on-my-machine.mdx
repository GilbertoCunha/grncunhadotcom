## The design, briefly

I don't want to spend too much time on how to design a URL Shortener, since it is System Design 101 and has been covered to death.

If it's new to you and you'd like to learn about design choices and trade-offs, you can read more about it in [ByteByteGo](https://bytebytego.com/courses/system-design-interview/design-a-url-shortener).

Here are the most important decisions made for the system I'm showcasing:

1. 100M urls a day equals around 1.2k writes and 11.6k reads per second. I aimed for a total of 10k rps with that same 10:1 ratio of reads to writes, as a real url shortener would see
2. I use MD5 hashing. With 365B urls (100M a day for 10 years), collisions are still very unlikely, and if *a few* collisions happen, they'd have negligible difference in overall latency. Plus, when using hashing, I don't need to maintain a separate service such as ZooKeeper for centralized ID generation (such as when using approaches such as base62 encoding). As a consequence, my overall system ends up being simpler, with fewer moving parts.
3. I'm not concerned with storing all urls for 10 years since I wouldn't have the storage capacity in my system (~28TB for my use case). I treat URLs as expiring after 24 hours (*which I have not yet implemented, to be completely honest*) which caps storage at around 8GB.
4. I use temporary redirects (HTTP status code 302) instead of permanent redirects (HTTP status code 301) to allow me to capture click rate - *and haven't implemented it either*. I'm lazy, you know?
5. Use a cache (Redis) in front of a database (Postgres) for reads
